# SO101 仿真任务场景系统 — 搭建计划（中期答辩版）

> 定位：把 `vla-manipulator/simulation` 现在"**一个场景 + 8 个物体 + 一句指令 + 一个判据**"
> 的抓取 demo，升级成"**任务族 × 分级 × 每级只加一个难度轴**"的场景系统，
> 每一级都带自动判据、指令池、可解性自检、随机化记录和答辩卡片；
> 并且**完全不动观测/动作格式**，所以在 AutoDL 上跑的 π0.5 训练链路零改动即可吃新数据。
>
> 方法论来源：`WYSD/underwater_sampling`（分级注册表 + 自检）、`WYSD/obstacle_grasp`
> （单一难度轴 + 实测数字）、`WYSD/Lerobot-Uranus-VLA-Demo/docs/underwater_vla_task_design.md`
> （观测/语言/动作/判据四旋钮纪律）。
>
> 本文是**计划**，不含实现。分节可独立验收。

## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
|---|---|
| 现在缺什么？ | 只有"抓起来"，没有"放到哪"；场景硬编码在 `assets/scene.xml`；判据写死在 `env._info()`；指令是 `objects.prompt` 一句；没有场景自检、没有卡片、没有评测矩阵。 |
| 怎么改？ | 加一层 **`TaskSpec` 注册表 + `TaskEnv`**：场景 XML、布局采样器、判据、指令池全部数据化；`_info()["success"]` 改成"注册表给的判据 + 保持时长"。 |
| 先做哪个族？ | **P1（抓取→放到圆盘）** 是所有后续任务的地基 → **P2（语言指称）** 是"语言分支是否被用上"的最小实验 → **O1~O5（几何障碍）** 是难度阶梯 → **V3（水下成像）** 作为交叉轴与**主图之一**。 |
| 叙事主线（已定） | **延续"水下"**：V3 直接复用 `WYSD/underwater_vision` 的 Jaffe 成像模型，与 `underwater_sampling`/`obstacle_grasp` 的工作衔接；"水下 × 几何障碍"的二维矩阵就是这条线的收口。 |
| **水下对比（硬要求）** | **每一级、每一个任务都必须产出成对的「无水下渲染 / 有水下渲染」**：同一 `seed`、同一布局，唯一变量是成像。**采集成对、评测成对、卡片成对**——只有一侧的等级视为"没做完"。 |
| 中期前的规模（已定） | **不追数据量**。每级只要求：判据可自动判 + 专家/人手可解 + 冒烟采集走通全链路（5 条）；大规模采集放到答辩后。 |
| 会不会破坏现有训练链路？ | 不会。动作维度仍是 6（5 关节 + 夹爪），观测仍是两路 224²，`task` 仍是文本。**障碍物与容器都是静态 body，不加关节。** |
| 最大的技术风险？ | ~~SO101 只有 5 自由度、只能竖直接近，绕障尺寸必须实测~~ → **M0 已量完**：包线见 [`SO101_ENVELOPE.md`](SO101_ENVELOPE.md)。新的风险是"**只能竖直抓取导致侧向障碍无效**"（O2/O3 原设计已被否），以及"专家在随机化区间内是否仍 100% 成功"。 |
| 答辩上最值钱的三张图？ | ①难度阶梯图（O1 为标尺，各级成功率差值可归因）②语言消融（同状态换指令，动作是否改变）③成功率–视觉退化曲线。 |
| 绝对不要做？ | ①为了加任务而加关节（会废掉已训好的 π0.5 适配）②一次堆 10 个任务把数据摊薄 ③时间驱动的专家（现有 `scripted_pick` 是里程碑式，必须保持）④只加一层滤镜就说"视觉退化"。 |

### 1.2 缺口（就是本计划要补的东西）

1. **没有"放置"**：`success` 只认"举起 6cm"，场景里没有 `place_target`，专家没有 place 阶段。
2. **场景不可配置**：`assets/scene.xml` 把 8 个物体和台面写死；`build_model()` 无参数。
3. **判据写死**：新任务想加一条判据必须改 `env.py`。
4. **没有难度分级**：8 个物体是"物体分布"，不是"难度阶梯"，讲不出"加一个障碍要付多少代价"。
5. **指令是常量**：`objects.BY_NAME[target].prompt` 一句，没有模板池 / hold-out，语言消融做不了。
6. **没有场景自检**：新摆位是否 IK 可达、障碍是否与臂干涉、静置是否稳定、判据会不会"白送成功"——全靠人眼。
7. **没有答辩素材生成**：没有卡片图、没有难度阶梯图、没有结构化评测 JSON。
8. **随机化参数不落盘**：`manifest.jsonl` 里没有 `task_id / level / instruction / layout_seed / params_hash`，消融实验不可复现。

## 2. 设计纪律（8 条，来自 WYSD 已踩过的坑）

1. **任何任务必须同时定义 4 个旋钮**：观测分布、语言–任务分布、动作/本体、评测判据。少一个就没法训练也没法评测。
2. **每级只加一个难度轴**，且必须有**无障碍基线**（标尺）。任意两级成功率之差才能直接归因。
3. **每个任务必须有 `env.success()`**，几行代码判不出来的任务先别做。判据要有**负对照**（"专家故意不做"时必须为 False）。
4. **专家必须是反应式里程碑控制器**，禁止时间驱动轨迹（同一状态→唯一动作）。新增 place 阶段尤其要注意。
5. **动作语义不许退化**：`action` 是"目标关节角/夹爪命令"，不是"当前状态"（否则闭环里策略停在半空）。
6. **随机化范围必须限制在专家 100% 可解的区间内**，否则采到的全是失败样本，策略学会"放弃"。
7. **同一场景不同指令** 必须能在数据里形成"语言–行为"配对；指令池 ≥3 训练模板 + ≥1 hold-out（hold-out 只评测、不进训练）。
8. **不许为了"任务多"摊薄数据量**：宁可 3 个任务各 100~200 条，不要 10 个任务各 30 条。
9. **每个任务都必须有成对的清晰 / 水下渲染**（同一 `seed` 与布局，唯一变量是成像）：两侧数据、两侧评测、两侧卡片。渲染层不是"某一个族"，而是**所有等级都要挂**的公共轴。

### 3.2 唯一真值表：`TaskSpec`

```python
@dataclass(frozen=True)
class TaskSpec:
    task_id: str                     # "o3_front_overhang"
    family: str                      # "P" / "O" / "L" / "D"
    level: int                       # 阶梯序号，P/O 各族各自 0..n
    title: str                       # "O3 前方低梁"
    scene: str                       # "scenes/o3_front_overhang.xml"
    difficulty_axis: str             # 一句话：这一级新增的难度轴
    criterion_text: str              # 判据的人话描述（卡片上直接印）
    instructions: tuple[str, ...]    # ≥3 训练模板
    holdout: tuple[str, ...]         # ≥1，只评测
    sample_layout: Callable[[np.random.Generator], dict]
        # -> {"props": {name: pose7}, "statics": {name: pose3}, "goal": (x, y), "vfx": {...}}
        # 唯一的随机性来源；障碍物/容器必须随目标一起动，难度关系才不漂移
    success: Callable[["TaskEnv"], bool]
    hold_s: float                    # 判据需连续成立多久（默认 0.4s）
    settle: Callable[["TaskEnv"], bool] = lambda env: True   # 初始布局是否合法
    expert: str = "pick_place"       # 复用哪个专家
    notes: str = ""                  # 实测数字/踩坑，直接进卡片
```

注册与查询（照搬 `WYSD/obstacle_grasp/tasks.py` 的形态）：

```python
LEVELS: dict[str, TaskSpec]           # task_id -> spec
LEVEL_ORDER: list[str]                # 按 (family, level) 排序
def get(task_id: str) -> TaskSpec
def describe_all() -> str             # 阶梯表，直接打印
```

### 3.3 `TaskEnv` 的扩展点

`SO101TabletopEnv` 保留不动（向后兼容、已在服务器上跑）。新增：

```python
class TaskEnv(SO101TabletopEnv):
    def __init__(self, task_id: str, *, vfx: WaterLikeParams | None = None, **kw)
    # reset: 用 spec.sample_layout 摆放 props，记录 init_props / init_qpos / layout_seed
    # info(): {"success": spec.success(self) and self._held(criterion, spec.hold_s), ...}
    # 判据零件（公共 API，判据函数只准用这些）：
    def prop_pos(self, name) -> np.ndarray            # 世界坐标
    def init_pos(self, name) -> np.ndarray            # reset 后的初始位置
    def moved(self, name) -> float                    # 相对初始位置的位移
    def goal_xy(self) -> np.ndarray                   # place_target 的 xy
    def on_goal(self, name, tol=0.025) -> bool        # 水平落在目标区 + 高度回到静置
    def in_container(self, name, tol_x=...) -> bool   # 容器内（水平 + 低于壁顶）
    def grasp_open(self, tol=0.1) -> bool             # 夹爪已张开（松手了）
    def rested(self, name, tol=0.004) -> bool         # 已静置（速度 + 高度）
    def max_contact_force(self, name) -> float        # 接触力峰值（D 族用）
    def hinge_angle_deg(self, name) -> float          # 铰链体绕轴累计角（D3 用）
    def vfx_params(self) -> dict | None               # 本 episode 的成像参数
    def spec_hash(self) -> str                        # 本 episode 的规格指纹（追溯用）
```

**三条语义纪律（来自 `WYSD/underwater_sampling`）**：

1. **`success`（即时几何）与 `settled`（真停稳）分离，且 `settled` 内含 `success`**：`success` 判"这一刻满足几何"，`settled` 额外要求速度≈0、没在飞。采集时用 `settled` 更严（`manual.is_placed = success and settled`）。
2. **`_held()` 语义**：把判据包成"连续成立 `hold_s`"，避免"路过即成功"（`obstacle_grasp` 的 `o5` 就是靠这个区分"举着经过圆盘"和"真的放下"）。
3. **`info()` / `metrics()` 必须带 `spec_hash` + `seed` + `layout`**：否则一次消融实验无法复现，也无法解释"为什么这级成功率是 62%"。

**布局注入机制（不要在 XML 里写死坐标）**：`_apply_layout()` 统一走三条路——
`props`（带 `freejoint`）→ 写 `data.qpos[adr:adr+7]`；`statics`（障碍/容器）→ 写 `model.body_pos`；`joints` → 写 `data.qpos`；最后 `mj_forward`。
遍历 `njnt` 自动建立 `prop_adr` / `prop_body_id` 映射（**不要按等级硬编码 qpos 下标**，加一个物件就会错位）。

### 3.4 场景 XML 的组织

- `base_table.xml`：`<include file="../../so101/assets/so101_new_calib.xml"/>` + `compiler/option/visual/asset` + 台面 / 地面 / 桌腿 / 背景板 / 两盏灯（**原样搬 `mj_env/assets/scene.xml` 里的这些块**，它们已经被相机与光照调过）。
- `scenes/<level>.xml`：`<include file="../base_table.xml"/>` + **只声明这一级新增的东西**：
  - 静态件（障碍、导墙、容器）→ 无 `freejoint`（不是 qpos 的一部分），位置由 Python 在 reset 时写 `model.body_pos`（见 §3.3 的注入机制）
  - 动态件 → 带 `freejoint`，命名遵循约定（见下）
- **命名约定**（沿用现有底座，`objects.py`/`layout.py` 零改动即可复用）：
  - 被操作物：`object`（`object_free` / `object_geom`）
  - 目标区载体：`place_target`（带 `place_target_site` 或 `place_target_geom`）
  - 干扰/障碍：`distractor_*`、`occluder`、`overhang`、`slot_wall`、`cover`
  - 容器：`container`（内腔尺寸由 `props.py` 从 `geom_aabb` 量出来）
- 两路相机与腕部相机仍在 `scene.py` 里用 `MjSpec` 注入（`so101_new_calib.xml` 保持纯硬件描述，这个约定不要破）。
- **keyframe 陷阱**：若分级场景里写 `<keyframe>`，`qpos` 必须按 freejoint 声明序**写满整串**（SO101 侧 = 臂 5 + 夹爪 1 + 每个 freejoint 7）。只写一部分 MuJoCo **静默错位、不报错**（`WYSD` 的场景里已经踩过这个坑）。建议新场景**干脆不写 keyframe**，初始位姿全部由 `sample_layout` 给。
- **`__init__.py` 用 `__getattr__` 惰性导入 `TaskEnv`**，这样 `import mj_env.specs` 本身不需要 mujoco，写判据测试和 CI 都轻（照搬 `underwater_sampling/__init__.py`）。

> 为什么不把所有东西塞进一个 XML：每级一个 XML 才能在 MuJoCo 里**单独打开检查**（`python -m mujoco.viewer --mjcf scenes/o3_....xml`），也才讲得清"这一级加了什么"。同时 `props.py` 的量尺寸逻辑保证 XML 与 Python 不会漂移（`objects.py` 已经证明这个模式有效）。

## 4. 任务族设计（内容）

### 4.1 P 族 — 放置与语言（**地基层，最先做**）

| 级 | 名称 | 新增难度轴 | 判据 | 指令池 |
|---|---|---|---|---|
| **P0**（已有） | 抓起来 | 基线：`grasped and lift ≥ 6cm` | 现状 | `pick up the red cube` |
| **P1** | 放到圆盘 | **多了"放到哪"**：需要把物体搬运到指定区并松手 | 物体水平落在 `place_target` 上（<25mm）+ 已静置 + 夹爪张开 | 3 句 + 1 hold-out |
| **P2** ✅ | 语言指称 | **语言必须被读**：场景放 **2 个同尺寸**方块（红 `object` / 黄 `object2`），句子说是哪一个 | **指定**那个落在圆盘上，且**另一个位移 <10mm** | 6 句 + 2 hold-out（每句都映射到一个 body） |
| **P3** ✅ | 放进容器 | **目标是一个体积而不是一个点**：有壁，手必须下进容器里 | 方块位于 `container_cavity` 内腔（内缩 8mm）+ 已静置 + 夹爪张开 | 3 句 + 1 hold-out |
| **P4** ✅ | 堆叠 | **垂直精度 + 不扰动**：放到另一个**自由体**方块上 | 目标中心落在支撑顶面 ±4mm、水平 ±15mm + 已静置 + 夹爪张开，且**支撑位移 <10mm** | 3 句 + 1 hold-out |

- **P1 是地基**：O 族全部沿用 P1 的"落到圆盘"判据，这样 O1 与 O2~O5 才有可比性；也是唯一能与现有 320 条 pick 数据对齐、证明"新判据没有作弊"的等级。
- **P2 的第二个物体就是语言消融装置**：如果换指令后动作不变、或者抓的还是原来那个 → 语言分支没被用上。这是最便宜、最有说服力的一张图。
- **P3 的尺寸是实测后的修正值**：内腔 **120mm**（半宽 60mm）、壁高 45mm。第一版取 110mm（对钳口较宽一侧 48.9mm 有 6mm 名义余量）**被自检抓到穿墙 0.54mm**——固定指比齿面中点**更低**，名义余量不等于实际余量。
- **P4 的堆叠高度是量出来的**，不是写死的：`TaskSpec.place_height` 读支撑块的**实际**位置，所以支撑块在静置中下沉零点几毫米也不会让高度失真，并且五级共用一个专家。

### 4.2 O 族 — 几何障碍（把 `WYSD/obstacle_grasp` 的分级思想平移到桌面）

| 级 | 名称 | 障碍物 | 新增难度轴 | 判据 |
|---|---|---|---|---|
| **O1** ✅ | 开阔基线 | 无（对照组） | 基线：视野与路径都通畅 | P1 判据 |
| **O2** ✅ | 只能抓窄面 | 70×16×22mm 的条：只有两条窄面能抓，**颌必须对齐长轴**否则合不上 | 感知物体朝向（抓取宽度是 16mm 窄面，不是长向） | P1 判据 |
| **O3** ✅ | 腕部遮挡 | 目标外侧 **76mm** 处一面 **100×6×46mm** 的挡板（遮挡腕部相机） | **看得见但看不清**：实测遮住目标 **13.5%** 的像素 | P1 判据 |
| **O4** ✅ | 窄缝插取 | 两堵导墙，**缝宽 106mm**、墙高 **45mm**，随目标一起旋转 | 毫米级横向精度（每侧 4mm 余量） | P1 判据 |
| **O5** ✅ | 覆盖堆叠 | 另一块方块**正压在目标上** | **顺序**：不先搬开就根本抓不到；整段约是其他级的两倍长 | P1 判据 **+ 覆盖块已落到台面、离目标 >50mm** |

> **原 O3′「单向进给」已取消，改成本表的 O2。** 对一台**只做垂直下探**的臂来说，围栏的
> 开口方向不构成任何约束：手是垂直进去的，只有**内腔尺寸**有约束，而那正是 P3。原先
> 设想的"钳口必须转到开口方位"预设了侧向进给——这台臂没有侧向进给。

**M0 否掉了 O2/O3 的原始设计**（数字见 [`SO101_ENVELOPE.md`](SO101_ENVELOPE.md) §5.1 与 §6）：

- **O2**：俯视相机在正上方 ⇒ 视线近乎垂直 ⇒ 立板要么贴到目标 50mm 内（那里是钳口走廊），要么高到 117~470mm（那里机械臂净空只有 62~240mm）。**两个约束永不相交。**
- **O3**：整条轨迹在近侧的最低点是 **139mm**，而就位姿态腕部在近侧是 **177mm** ⇒ 清得过梁的梁挡不住抓取，挡得住抓取的梁一定撞臂。**根因：SO101 只能竖直抓取，径向剖面是"细柱子 + 远处高台"—— r<49mm 是手（直落到台面），r≥50mm 之外只有 ≥139mm 的腕部。任何 r≥50mm 的竖向障碍都挡不住下探。**
- 所以 O 族的难度必须建在**"限制那只 83mm 宽的手能从哪里下去"**上，而不是"在侧面挡一根梁"。

- **O2′ 的遮挡率**：M0 已给出俯视方案不可行的完整证据链；改遮腕部相机后，仍然用 `obstacle_grasp` 那套**像素差**方法实测：`m_obj_full = |藏遮挡 − 都藏|`，`m_obj_visible = |正常 − 藏目标|`，遮挡率随布局稳定才算通过。
- **O3′ 的开口宽度**：下限由手部外廓 **82.8mm** 决定（90mm ⇒ 每侧 3.6mm），墙高上限由 `H(45mm)=54.7mm` 决定（取 45mm）。这套"三面围栏"的尺寸可以用同一个 `envelope_probe.py` 的方法继续量。
- **O4 的缝宽**：**已经量出** —— 下探姿态（43mm 开度）手部外廓 **82.8 × 82.6 mm**，闭合时也有 74.5mm 宽；90mm 缝 ⇒ 每侧 3.6mm，100mm 缝 ⇒ 8.6mm。想调难度就改缝宽。
- **随机化纪律**：**障碍物/容器随目标一起移动**（在 `sample_layout` 里用目标的 xy 推导障碍 xy），否则"障碍与目标的关系"会随随机化漂移，难度就不可归因了。

### 4.3 成像轴 — **每一级都要有的 clean / underwater 成对对比**

这一族**不是可选交叉项，是所有等级的公共条件**：每个任务都跑两遍，一遍无水下渲染、一遍有水下渲染。

**配对纪律（不配对 = 实验作废）**：

| 项 | 要求 |
|---|---|
| 布局 | **同一 `seed` → 同一布局**（物体 xy/yaw、障碍位置全同） |
| 唯一变量 | 只有成像（`vfx`）不同 |
| 记录 | `vfx.preset` + `Params.hash()` 写进 manifest；配对的两条 episode 必须 `layout_seed` 相同、`vfx_hash` 不同 |
| 校验 | 自检里断言"同 seed 下 clean 与 water 的 `init_props` 逐位一致" |
| 命名 | 每级两个 staging 目录：`<level>_clean` / `<level>_water` |

**水下档位（`underwater_vision` 的三档 + 能见度换算）**：

| 档 | 名称 | 图像域处理 | 用途 |
|---|---|---|---|
| **V0** | 无水下（clean） | 不做任何后处理 | **每一级的对照侧** |
| **V1** | 轻浊 / 低对比 | 弱分通道衰减 + 弱背向散射 + 轻微对比度压缩 | 稳健档 |
| **V2** | 中浊 | 中等衰减 + 背向散射 + 噪声 + JPEG 伪影 | 主实验档 |
| **V3** | 重浊 / 低能见度 | 强衰减（红光先没）+ 强背向散射 + 模糊 + 暗角 | 难度上限 |

- **主图变成"每任务 × 两档成像"的成对柱状图**（clean 与 water 相邻成对），而不是一条孤立的退化曲线。这样每一级都有对比，也一眼能看出"哪些任务更怕水"。
- 深度 `d(x)` 用 `underwater_vision` 的 `Renderer` 深度通道（SO101 相机距目标仅 ~0.5~0.7m，**β 与 `depth_scale` 必须为本场景重新标定**，不能照抄 Uranus 的 1.2~2.0m 工作半径；`stat.extent=1.85`，雾类参数即便在 MuJoCo 里也无效，见下）。

**工程铁律（来自 WYSD 的教训，会直接毁掉实验）**：
1. 同一个函数必须**同时**挂在采集端与评估端（否则训练/评测成像不一致，数字无意义）。
2. 参数（`β/B_c/噪声σ/JPEG质量`）与 `seed` 必须**记进 manifest 与数据集旁边的 JSON**，附参数哈希。
3. MuJoCo ≥3.8 的 classic renderer **不读 fog/haze**（`mjRND_FOG/HAZE` 无效，`MjvScene` 无 fog 字段），所以**视觉退化只能在图像域做**；MuJoCo 侧只留 `<light>` 与 `headlight`。
4. 不要做折射/焦散（相机标定与 IK 会全错）。

> 可复用资产：`WYSD/underwater_vision/`（`WaterParams` / `WaterRenderer` / `SceneStyle` / `xml_visual_snippet`）已经把 Jaffe 模型、三档预设、能见度换算、参数 `to_json/hash` 写完了。SO101 侧只需换相机名，**建议直接 import 而不是重写**（`PYTHONPATH` 加 `WYSD`）。

### 5.1 M0 的第二半：成像标定（因为每一级都要有水下对比）

要量出来的数字（`scripts/water_probe.py`）：

| # | 量 | 方法 | 用途 |
|---|---|---|---|

| 2 | 三档水况下的对比度 / 边缘能量 / 信噪比 | 同一帧过 `WaterParams` 三档 | **把档位调到"有梯度但目标仍可见"**（参考 WYSD：clear 0.81 / coastal 0.56 / turbid 0.28 / harbor 0.22） |

### 5.2 M0.5 实测结果（✅ 已完成）

Uranus 的预设参数在 SO101 上**几乎无效**：`coastal` 只让目标对比度动了 5%。原因是光程——Uranus 相机距工作面 1.2~2.0 m，SO101 的俯视相机只有 0.66 m，`exp(-β·d)` 根本压不下来。所以按**能见度（米）** 重标（`β ≈ 3/能见度`），这是能印在 PPT 上的物理量：

| 档 | 能见度 | **俯视相机**相对信号 | 腕部相机相对信号 | 背景噪声 |
|---|---|---|---|---|
| `v0_clean` | — | 1.000 | 1.000 | 58.8 |
| `v1_light` | 3.00 m | 0.737 | 0.911 | 73.0 |
| `v2_medium` | 1.20 m | 0.488 | 0.827 | 64.3 |
| `v3_heavy` | 0.60 m | **0.218** | 0.699 | 46.0 |

- "相对信号"＝目标区域与紧邻背景的**亮度差**相对清水的比例。三档单调下降、都有梯度。
- **腕部相机比俯视相机鲁棒得多**（v3 还有 0.699）：它离目标只有 6cm，光程短。**所以水下的难度主要由俯视相机承担**——这是一个可以直接讲的结论，也决定了"哪一路相机消融"会出差异。
- 视觉上 `v3` 里**红方块先变成深灰**（红光先衰减），蓝盘仍然清楚 —— 正是 `WYSD` 文档里"黄/红物体是天然消融对象"那条。

**三个测量陷阱（都踩过，写下来免得重犯）**：

1. **RMS 对比度是错的指标**。背向散射与颗粒会**增加**高频结构，所以退化越重、RMS 对比度反而可能越高（实测：背景边缘能量从 59 升到 73）。必须用"目标 vs 背景亮度差"这类噪声会被平均掉的量。
2. **一个臂位姿不能同时测两路相机**。抓取位姿下**手把目标从俯视相机里完全挡住（掩码 0 px）**——这正是 `WYSD` §2.5 第 4 条"自遮挡"在 SO101 上的实测；而 HOME 位姿下腕部相机看的是空桌面。所以每路相机在"它确实看得见目标"的位姿下测，并把位姿记进配置。
3. **雪点不是难度轴**。`from_visibility` 会把整套参数一起缩放，能见度低于 1m 时满屏亮点，看起来"难"其实是"读不出来"。颗粒层加上限（密度 0.55 / 亮度 0.30），衰减与背向散射保留。

**配对已经过验证**（`mj_env/test_vfx.py`，7 项全过）：

- `clean` 档渲染与父类**逐像素一致**（回归：控制侧没有被改动）；
- 同 seed 两侧 `layout` / `init_props` / `goal_xy` **逐位相同**，`vfx_hash` 不同；
- 成对冒烟：同一批 seed 跑 clean 与 v2_medium，**落点误差逐位相同**（3.1 / 2.7 / 4.3 / 3.7 mm）→ 专家对成像免疫，两侧轨迹完全一致，**唯一变量就是图像**。这正是这条对比轴要的性质。

> ⚠️ 因此：**专家是"成像盲"的**，clean 与 water 两份数据的动作完全相同、观测不同。这正是视觉鲁棒性实验需要的对照；不要在采集端对水下档做任何额外的专家调整，否则"唯一变量是成像"就被破坏了。

## 6. 判据库（`specs/criteria.py`）

只允许用 `TaskEnv` 暴露的公共方法写判据，判据函数必须是纯函数（`TaskEnv -> bool`）。

```python
def on_place_target(env, tol=0.025) -> bool:
    """物体真的落在目标区上（不是被举着经过）。"""
    return env.on_goal("object", tol) and env.rested("object") and env.grasp_open()

def in_container(env, name="object") -> bool:
    return env.in_container(name) and env.rested(name) and env.grasp_open()

def undisturbed(env, name, tol=0.010) -> bool:
    """干扰块/基块没被撞移位。"""
    return env.moved(name) < tol
```

**负对照测试（必须有）**：对每个判据写一个"专家不做这一步"的用例，断言判据为 `False`。
例：P1 判据在"只举起来没搬运"、`o5` 判据在"举着目标从圆盘上方经过"这两种情况下都必须 False。

## 8. 数据与训练对接（与 AutoDL 那部分人的接口）

### 8.1 冻结的东西（不要动）

| 项 | 值 | 原因 |
|---|---|---|
| `state` / `actions` | 6 维（5 关节 + 夹爪，归一化电机坐标） | 已训好的 π0.5 适配器按这个写 |
| 图像 | `image` + `wrist_image`，224×224 uint8 | `lerobot_features()` 固定 |
| 频率 | 20 Hz，`timestamp = frame/fps` | `SynchronizedEpisodeRecorder` 严格的均匀性校验 |
| 帧配对 | `observation[t] -> action[t]` | 同上 |
| `task` | 文本，一个 episode 唯一 | `StagingDataset.save_episode` 强制 |

**推论：新增的障碍物、容器、圆盘、视觉退化全都不改 schema → 现有转换/归一化/训练脚本零改动。**

### 8.2 `manifest.jsonl` 新增字段（不改 `.npz` 内部）

```json
{"episode_index": 0, "path": "episodes/episode_000000.npz", "frames": 137,
 "task": "put the red cube on the blue disc",
 "task_id": "p1_place_disc", "family": "P", "level": 1,
 "target": "cube_red", "instruction_kind": "train",     // train | holdout
 "layout_seed": 10012, "layout": {"object": [x,y,yaw], "place_target": [x,y]},
 "vfx": {"preset": "coastal", "hash": "…"}, "expert": "pick_place",
 "success": true, "grasped": true, "lift_height": 0.14,
 "initial_qpos": [...], "outcome": "success"}
```

作用：①消融实验可复现（seed + 布局 + 成像参数）②`instruction_kind` 让训练集能排除 hold-out ③`task_id/level` 让评测能按级出成功率。

### 8.3 采集命令（服务器）——✅ 采集器已落地

**实际落地的是 [`collect_levels.py`](../simulation/mj_env/scripts/collect_levels.py)**（不是改
`collect_demonstrations.py`：那条是旧 8 物体路径，改它会同时动到 320 条基线数据的采集方式）。
它按注册表工作，所以**加新关卡不需要改采集器**。

```bash
# 成对采集：同一 layout seed 序列，唯一变量是成像
UV_NO_SYNC=1 MUJOCO_GL=egl PYOPENGL_PLATFORM=egl \
uv run python -m mj_env.scripts.collect_levels \
  --all --episodes 1 --vfx v0_clean --vfx v2_medium \
  --instruction-pool train --root /root/autodl-tmp/datasets/so101_staging/scenes_v1 \
  --height 224 --width 224 --headless
```

- `--task <level>` 可重复，或 `--all` 走完整阶梯；`--vfx` 可重复（缺省 `v0_clean` + `v2_medium`）。
- 输出结构：`<root>/<task_id>/<rung>/{episodes/,manifest.jsonl,metadata.json}` +
  `<root>/collection_results.jsonl`（**失败也记录**，这样"哪一级采不到"是可查的）。
- **指令在采集器里采样**，不在环境里：recorder 必须在 episode 开始前就拿到任务文本。
  让环境采样、事后再读 `env.task`，正是场景自检抓到"一整批 episode 被贴上默认 prompt"的原因。
  从声明的池子里采样也让 hold-out 句**在构造上**进不了训练集。
- **两侧必须用同一 `--seed` 与同一 `--instruction-pool`**。

**配对校验器**：[`verify_pairs.py`](../simulation/mj_env/scripts/verify_pairs.py) 直接在**落盘的
staging 数据**上验证不变量（不是只验环境）：

```
clean episodes: 1   water episodes: 1   paired: 1
  seed 0: frames=234 mean |clean-water| = 98.52
  schema: {'image=224x224': 2, 'wrist_image=224x224': 2}
  staged size: clean 6.4 MB, water 63.0 MB (water is 9.9x the clean size)
all 1 pairs satisfy the invariants
```

它断言：同 `layout_seed`、**动作流逐位相同**（专家对成像是盲的 ⇒ 只要动作不同，这一对就被
污染了）、状态流相同、任务文本相同、两路 224² 与 6 维 state/action、时间戳严格 20Hz、
两侧图像确实不同。**"动作流逐位相同"是这一整套成对设计最强的那条证据。**

> ⚠️ **实测的存储代价**：水下那一侧**是 clean 的约 10 倍大**（234 帧 63 MB vs 6.4 MB；
> O5 两阶段 496 帧：clean 28 MB vs water 267 MB，9.5×）。
> 原因是成像噪声几乎不可压缩（clean 图大片平坦，压缩率极高）。做规模预算时必须按
> **clean + 10×water** 算，不能按"两侧一样大"算。

**多试几个 seed、只存成功的**：`--successes N`（每级每档要存几条）与 `--max-attempts M`
（最多试几次，缺省 3×N）。循环顺序是 **seed 在外、档位在内**，所以两侧尝试的是**同一条
seed 序列**——某一侧失败只会让那一对少一条，而不会让两侧的 seed 集合错开。
汇总里报的是两侧 seed 集合的**交集**（"complete pairs"），不是两个独立的成功数。

**9 级成对冒烟实测**（`--all --successes 1 --max-attempts 2`）：

| 关卡 | clean | water | 配对 |
|---|---|---|---|
| o1 / o2 / o3 / o4 / p1 / p2 / p3 | 1/1 | 1/1 | 各 1 |
| p4_stack | 2/3 | 2/3 | **2** |
| o5_covered_stack | 2/2 | 2/2 | **2** |

P4 的 seed 0 是已知的 13.1mm 离群（见 §10.4），所以它第一次冒烟 0/1——**这正是"采集器必须
能多试几个 seed"的理由**：要求 seed 0 成功，等于把专家的偶发离群变成采集失败。

### 8.4 数据量预算

> **中期答辩阶段不追数量**（已定）。这一阶段的验收标准是"**每级能采**"而不是"每级采够"：
> 判据可自动判 → 专家/人手 20 组随机布局可解 → 采 5 条冒烟 → 走通转换/归一化/10 步训练。
> 下表是**答辩之后**规模采集的预算，现在只用来确认"这条路走得通"。

| 用途 | 每级条数 | 说明 |
|---|---|---|
| **配对对照（每一级必备）** | **clean 与 water 各 ≥100 条，同一 seed 序列** | 唯一变量是成像；这是"每一级都有水下对比"的执行方式 |
| **冒烟（中期前）** | **clean / water 各 5 条** | 只验证"这条路走得通"，不追数量 |
| 单级（P1/P2/P3、O1~O5） | **100~200 条成功** | 对齐现有 40 条/物体 → 320 条的基线；新任务比单物体抓取难，给到 100 起 |
| 语言 hold-out | **不进训练** | 只在评测用，≥1 句/级 |
| V 族消融 | 清/浊两套各 ≥100 条，**同一 seed 序列** | 保证唯一变量是成像 |
| 多任务混训（若做） | 每任务 ≥100 条，**总任务数 ≤4** | 不要摊薄 |

### 8.5 与训练方的三条约定

1. **数据划分**：训练 seed 从 `10000` 起，评测 seed 用 `1000~1019`（沿用现有约定，绝不重叠）。
2. **`task` 文本**：每级指令池 ≥3 句训练模板，逐 episode 随机抽一句（**同一场景不同指令 → 数据里天然含语言–行为配对**）；hold-out 句只出现在评测。
   ⚠️ **必须在 manifest 里写 `instruction_kind`（train / holdout）或 `instruction_split`**：`WYSD` 的做法是 75/25 把 hold-out 句**混进**抽样，结果要跑消融时必须回头按字段过滤——如果当初没记，训练集里就混进了 hold-out，语言泛化数字直接作废。SO101 侧从一开始就记。
3. **命名**：LeRobot 数据集标识沿用 `HF2147552431/so101-mujoco-*`；新数据集建议 `so101-mujoco-scenes-v1`，与现有 `so101-mujoco-pick` 分开，避免覆盖已训实验。

**过程中最花时间的一个问题（已解决）：物体在搬运途中从夹爪里"走"出来。** 这是夹持质量问题，不是架构问题。证据链：

| 观察 | 数值 |
|---|---|
| 失败都是横向落点偏差 | 27~78mm（成功的只有 2~23mm），双峰分布 |
| 关节是连续的，不是 IK 跳分支 | 沿路径最大关节跳变 4° |
| 姿态沿路径本来就漂 | 相对抓取位姿 20~50°（所以"姿态门槛"没有物理意义，已去掉） |
| **物体悬在齿面中点下方** | **12~21mm**（软接触 + 重力），横向再偏 6~19mm |
| 把搬运距离从 0.35m 收到 0.20m | 10/12（明显改善，说明是**累积**效应） |
| 用实测偏移做闭环落点补偿 | 精度变好（2.5~13mm）但总数 8/12，仍有横向滑脱 |
| **搬运越慢掉得越多** | 4mm×3 步 比 8mm×1 步 更差 ⇒ **持续夹持下的接触蠕变**特征 |

**结论（已解决）：真正的原因是"夹得太紧"。** 手指垫面与方块的接触是软的，把一个刚性方块用位置伺服**压进 8mm**，会让它进入一种"持续蠕变"的状态——搬运要好几秒，它就被慢慢挤出来。**夹得轻反而抓得牢**：摩擦承担握持，干涉只用来建立接触。

同一 12 组布局上的实测（垫面摩擦保持出厂值 1.5）：

| 夹持干涉（每侧） | 成功率 | 最大落点误差 |
|---|---|---|
| **2 mm** | **12/12** | **10 mm** |
| 4 mm | 11/12 | 39 mm |
| 8 mm | 7/12 | 65 mm |

**20 组验收：12/12 → 20/20（100%），落点误差中位 3.7mm、最大 18.5mm。**

顺带否掉的两个假设（都被实测打掉，记下来免得重试）：

| 假设 | 实测结果 |
|---|---|
| 调硬手指 `solref` 到 0.002（`WYSD` 对 Uranus 手用过的招） | **0/12，误差 ~190mm**：硬接触 + 位置伺服会在合爪瞬间把方块弹飞 |
| 姿态漂移把方块"拧"出去 | 沿路径姿态本来就漂 20~50°（相对抓取位姿），**抓取路点自身也漂 8~48°**，且关节连续无跳变 ⇒ 不是原因，姿态门槛已删除 |
| 搬运越慢越稳 | 反过来：4mm×3 步比 8mm×1 步更差 ⇒ 是**时间累积**效应，加快缩短暴露时间有帮助 |

其余两项落地改动同样重要：**搬运必须走极坐标弧线**（直线会把机械臂带到 r≈0.15 的底座附近，那里 5 自由度无解），以及**落点要按实测的"物体相对齿面中点"偏移做闭环补偿**（软接触让方块悬在齿面中点下方 12~21mm，直接命令齿面下到台面会把方块顶到桌面再挤飞）。

### 10.2 O4 窄缝：一个尺寸算错一个量级，以及它牵出的专家不一致

O4 第一版只有 **2/8**，诊断显示"手与导墙有 −1.1~−1.9mm 穿透"，失败时方块根本没被拿起来。三步定位：

1. **手部外廓是不对称的**。M0 表里 `outer_half_span_closing = 48.9mm`，但 `span_closing = 82.8mm` —— 说明齿面中点**偏心**：一侧突出 48.9mm，另一侧只有 33.9mm。先前按"82.8/2 = 41.4mm"算缝宽（还写了"90mm 缝每侧 3.6mm"）**是错的**；较宽那一侧单独就需要 48.9mm。缝宽不是 90mm，而是 **106mm = 2×(48.9 + 4mm)**。
2. **但 106mm 仍然撞**（穿透 −4.6mm，撞的是 `fixed_finger`）。补测才发现：**脚本专家下探时用的是 57mm 开度**（`width + JAW_CLEARANCE`），此时手宽 **130.3mm**；而路径解算 `solve_aperture` 用的是 **43mm 开度**的齿面中点 —— **专家自身不一致**：IK 按 43mm 开度把齿面中点对到物体上，实际却用 57mm 开度降下去，齿面中点自然偏了。
3. **修法**：让专家在 `reach`/`grasp` 两段把夹爪收到 **43mm 开度**（`PlaceTuning.approach_clearance = PAD_CLEARANCE`），只在 hover 段保持大开口。手宽降到 **82.8mm**，与 IK 的假设一致。

修完的结果：

| 任务 | 结果 |
|---|---|
| O4 窄缝（12 组） | **12/12**，与导墙的穿透 **全为 +0.000mm**，落点误差中位 3.7mm |
| P1 回归（12 组） | **12/12**（未受影响） |
| O1 回归（6 组） | **6/6**（未受影响） |

**教训（已写进代码注释）**：*"手部外廓"必须说明是**哪个开度**下的外廓，并且必须与 IK 的齿面中点假设一致；只说"82.8mm"会让人以为缝能做到 90mm。* 这条也意味着 M0 的外廓表与 `H(A)` 要**按开度索引**，否则 O3′/O5 还会再错一次。

### 10.3 P2 语言指称：判据要能"扣分"，采样器不能借用过严的 margin

**判据设计**。P2 的判据不是"指定方块落在圆盘上"，而是**再加上"另一个方块位移 <10mm"**。原因是：一个完全不看指令、永远抓红方块的策略，在两级场景上能拿 **50%** —— 而这个数字恰好会把"语言分支根本没被用上"盖住。加上这一条，抓错方块直接判失败，成功率就是诚实的 0%。

同理，**两个方块必须同尺寸**（都是 35mm，只有颜色不同）：尺寸或形状差异会让策略用轮廓走捷径，绕开语言。颜色选红/黄——正好是水下衰减曲线的两端，所以这一级也顺带显示成像轴先摧毁哪一个。

**工程坑**：第一版布局借用 `layout.sample_layout`，把它的 `margin` 设成 0.10 —— 于是**每一对**（两个方块之间、方块到圆盘之间）都要隔 100mm，在只有 ±55°、r∈[0.185,0.27] 的抓取带里几乎无解。实测后果是 **1.1 秒/组**，而且退化：两个方块永远隔 290mm、圆盘永远贴在窗口最远端。改成"先采圆盘、再各自对圆盘采方块"的定向拒绝采样后：**0.12 毫秒/组（快 9000 倍）**，方块间距中位 86mm、方块到目标中位 144mm，全部落在设计窗口内。

**实测（可直接进报告）**：脚本专家 6 个 seed × 2 句 → **跟随指令 12/12**、**同 seed 换指令后"落在圆盘上的是另一个方块" 6/6**、成功率 12/12。专家是"读指令"的（拿到特权目标），所以这证明的是**装置能表达这个实验**，不是策略学会了；把同一张表换成训练好的 checkpoint 跑，同样的三列就是真正的语言消融结果。

### 10.4 从 4 级扩到 7 级：四个坑，以及一个"没有难度"的设计

这一轮把阶梯从 4 级扩到 7 级（P1~P4、O1/O2/O4），四个坑都值得记下来。

**① 判据里的绝对阈值会在换物体时静默失效。** `released()` 原本写死"夹爪开度 ≥ 50mm 就算松手"。
对 35mm 方块成立（释放开度 57mm）；对 16mm 细条，释放开度只有 38mm ⇒ **"已松手"永远为假**。
后果极具迷惑性：10 段里有 7 段落点误差 <3mm，全部判失败，而日志只会说"没静置"。
**改成相对判据**：`开度 ≥ 物体的 grip_width + 12mm`。任何写死的尺寸阈值，只要场景里会出现
第二种尺寸的物体，就一定会静默失效。

**② 采样器漏掉搬运窗口 = 再好的夹持也救不了。** O2 一开始自己采样物体和圆盘的位置，
**没有套用 P1/O4 都有的 `MAX_SEPARATION=0.20` 上限**。结果 3 个 seed 里 2 个把条子举到
190mm 后在**搬运刚开始的第 8 帧**脱落；夹持量从 2mm 扫到 24mm **完全没有改善**（越紧反而越差，
误差 86→151→225mm）。
**教训**：诊断"抓不住"之前先确认**搬运距离**在窗口内——症状（举起来又掉）和"夹持不足"一模一样。
现在所有单物体关卡都必须走 `sample_object_and_goal()`。

**③ 名义余量 ≠ 实际余量。** P3 的容器内腔第一版取 **110mm**，对钳口较宽一侧（48.9mm）有
6mm 名义余量，看起来绰绰有余；自检直接抓到**手指穿墙 0.542mm**。原因是**固定指比齿面中点更低**，
会在下探末段扫过内腔边角。内腔改到 **120mm** 后穿透 +0.000mm。
**这条与 §10.2 是同一个道理**：所有"能不能进去"的判断都必须看**下探姿态下、齿面中点以下**的实际外形。

**④ `base` 是机器人自带的 body 名。** P4 的支撑块最初叫 `base`，MuJoCo 直接报
`repeated name 'base' in body`。改名 `support`。场景合成会把机器人 XML 和场景 XML 并到
一起，所以**自定义 body 名必须避开机器人自带的命名**（`base`/`shoulder`/`upper_arm`/`gripper` 等）。

**⑤ 一个"没有难度"的设计：O3′ 单向进给。** 原设计是"三面围栏只留一个 90mm 开口，钳口必须
转到开口方位才进得去"。但**这台臂只做垂直下探**——开口方向对垂直进入没有任何约束，只有
**内腔尺寸**有约束，而那正是 P3。所以 O3′ 被取消，换成了 **O2「只能抓窄面」**：这个难度对
垂直下探是真实存在的（颌不对齐长轴就合不上，必须感知物体朝向），也是现有 8 物体目录里
已被证明会惩罚"冲着重心去"的那一类。

> 一条可复用的判据：**一个设计是不是"有难度"，取决于它约束的是不是这条臂实际会做的动作。**
> 侧向进给、绕过障碍的弧线、非垂直抓取——这些对一台 5 自由度、只做垂直下探的臂统统不存在。

### 10.5 O5 覆盖堆叠：多阶段关卡暴露的三处"单阶段假设"

O5 是全阶梯唯一需要**两次抓放**的关卡（先把覆盖块搬走，再抓被压住的目标）。加它的时候，
三处一直没被触发的"单阶段假设"同时暴露了。

**① 用关卡判据去判一个阶段，阶段永远失败。** 第一阶段（搬覆盖块）我最初用
`run_pick_place(...)["success"]` 判断成败，而这个字段是**关卡判据**——O5 的判据还要求目标
已上盘，第一阶段按定义不可能满足。后果是：覆盖块明明**落到了停车位 4.6mm 以内**，4 个 seed
全部报 `cover_failed`。**修法**：阶段用**自己的几何条件**判（落点 ≤30mm + 已落到台面 + 已松手）。
**教训**：多阶段任务里，"这一阶段做完了吗"和"整个任务成功了吗"是两个判据，不能复用。

**② 二维重叠检查会禁止合法的堆叠。** 自检的 `props_do_not_overlap` 只比 xy 距离，于是
"覆盖块压在目标上"被报成 2 次重叠。**改成三维**：只有**竖向也相交**才算重叠，并留 0.5mm
接触容差（两块方块的中心距正好等于半高之和，静置还会吃掉几微米，精确比较会把每个堆叠都判成重叠）。

**③ "障碍物随目标移动"的不变量对停车位不成立。** O4 的导墙必须随目标旋转，否则"离目标 53mm"
就不是关卡属性；自检把这条推广到了**所有** static。但 O5 的停车位必须躲开**同样随机**的目标，
不可能刚性跟随。**修法**：新增 `TaskSpec.independent_statics` 显式声明哪些 static 是按**关卡**
定位的，自检据此把它们标为"by design"而不是静默跳过——**显式声明**是关键，静默跳过会让这条
不变量以后再也检查不到东西。

**④ 顺带一条实现细节**：两阶段的第二段复用同一个 `run_pick_place`（只是 `reset=False`、
并显式指定 target 与落点）。如果第二段需要自己的动作，这一级就在同时测两件事，成功率无法
归因到"顺序"上。为此给 `run_pick_place` 加了三个参数（`target` / `place_xy` / `reset`），
其余动作路径**一字未改**——所以 O5 与 P1 的差可以干净地归因到"多了一阶段"。

**实测**：O5 专家 **5/5 = 100%**；覆盖块落点误差 0.7~8.5mm；目标落点误差 0.7~7.9mm。

### 10.6 O3 腕部遮挡：遮挡率的上限是**硬件**给的，不是设计选的

O3 的原始方案（俯视相机下挂立板）在 M0 就被否掉了。换成"挡腕部相机"之后，我先写了一个
`scripts/occlusion_probe.py` 去**量**，而不是画：它在抓取位姿渲染腕部相机三次
（有物体无墙 / 无物体无墙 → 物体的像素掩码 / 有物体有墙），对每个候选报三个数——
**遮挡率**、**离机器人最近距离**、**离目标最近距离**。

第一次跑（128 个候选）只有 5 个可用；把墙从"径向刀片"改成"切向隔板"后（192 个候选）
**遮挡率全是 0%**。原因查出来是两条硬约束：

1. **手指是沿目标局部 +x 排布的**（`grasp_axis_yaw` 返回的就是局部 +x），所以任何"长"的
   障碍只要落在钳口走廊里就会撞手；能靠近的障碍必须**在切向很窄**。
2. **目标的角会扫出一个圆**：35mm 方块的角半径是 **24.7mm**（不是面宽 17.5mm），而目标偏航
   是随机的 ⇒ 挡板的内端必须让开 24.7mm，否则在**某些偏航**下会插进方块里。这一条我是
   第三次踩"名义尺寸 ≠ 实际尺寸"了（前两次见 §10.2 与 §10.4）。

加上"离目标"这条判据后，24 个候选里只剩 **4 个**可用，最优解：

| 挡板 | 遮挡率 | 离机器人 | 离目标 |
|---|---|---|---|
| 100×6×46mm，偏置 76mm，方位 0° | **13.5%** | 13.6mm | 8.4mm |

**结论（要写进报告）**：腕部相机离抓取点只有 60mm，而挡板被两条硬约束推到 76mm 以外——
从这个距离，一块板**最多只能盖住目标的一个角（约 13.5% 的像素）**。
所以 O3 是一个**轻微的**感知障碍，不是"看不见"。这是**对这台硬件的测量**，不是设计偏好：
想做出更重的遮挡，就得允许挡板插进手指走廊或目标旋转扫过的区域，那会让这一级同时变成
"几何不可行"，从而无法把成功率差归因到成像上。

**顺带一条方法论**：这个探针复用了我一直用的"像素差求掩码 + 逐项净空"套路，但它这次
**主动告诉我一个设计做不到**——比画一张好看的图有价值。O3 的难度轴因此按实测写成
"看得见但看不清（遮住一角）"，而不是计划里写的"挡住部分视野"。

### 10.7 O5 暴露的那个"静置阶段没被录进数据"——影响的是**所有**关卡

O5 接进采集器后，**每一次尝试都抛 `ValueError`**（而单独跑专家是 5/5）。堆栈指向
recorder 的时序校验"non-uniform demonstration timing"。根因：

`run_pick_place` 结尾有一段**静置循环**（收尾后停 2 秒，让判据的 hold 时间走完），
它直接调 `env.step`，**没有把帧交给 recorder**。于是这 2 秒的仿真时间被跳过了。
对**单阶段**关卡，这段在整段的**最后一帧之后**，后面没有帧了，所以校验永远碰不到；
对 **O5**，它落在**两段之间**，第二段的第一帧时间戳一下跳了 2 秒 ⇒ 校验报错。

**修法**：让静置循环遵守和 `_glide` 一样的约定（先回调动作前观测、再 step）。

**但这件事的真正含义比 O5 大**：在这之前，**每一个关卡**采出来的 episode 都在
"松手 + 撤退 + 静置"之前就停止记录了 —— 也就是说，**判据被评估的那个阶段，策略在数据里
从来没看见过**。训练出来的策略会学到"放到圆盘上就结束"，而不知道还要松手、还要停稳。
这是一个**数据质量**问题，不是 O5 的问题；是 O5 的两阶段结构把它暴露出来的。

> 可复用的判据：**一个只在"最后一步之后"执行的代码路径，永远不会被任何测试碰到。**
> 这类问题需要**两阶段/多阶段的用例**才会现形——这也是为什么值得在阶梯里保留至少一个
> 多阶段关卡，而不是把它当成"锦上添花"。

## 11. 风险与坑（SO101 特化，按踩到概率排序）

| 坑 | 后果 | 对策 |
|---|---|---|
| **5 自由度只能竖直接近** | 绕障方案想当然 → 专家全失败 | O3/O4 的可行性**先由 M0 的腕部角度扫描确定**，再定障碍尺寸 |
| 静态障碍物被写进 XML 却带 `freejoint` | 障碍自己会动，难度漂移 | 静态件一律无 `freejoint`；自检第 3 项检查静置漂移 |
| 障碍物不随目标随机化 | 障碍与目标的关系变了，级间差值不可归因 | `sample_layout` 里由目标 xy 推导障碍 xy（照搬 `obstacle_grasp` 的做法） |
| 随机化范围超出专家能力 | 采到的全是失败样本，策略学会"放弃" | `check_reach` + 专家 `*_e2e.py` 回归限定区间；先窄后宽 |
| 判据"白送成功"（举着经过目标区） | 成功率虚高，实验全废 | `hold_s` + `rested()` + `grasp_open()`；`check_no_free_success` 负对照 |
| 专家改成时间驱动 | 任务对策略不可观测，BC 只学条件均值 | 保持 `scripted_pick` 的里程碑式结构；place 阶段同样按状态分支 |
| 为加任务而动动作维度（加关节） | 已训的 π0.5 适配器全废 | **不加关节**；障碍/容器都是静态 body |
| 图像退化只在采集端做 | 评测数字虚高/虚低 | 同一函数两端调用 + `params_hash` 写进 manifest 与数据集旁 JSON |
| **水下对比的两侧布局不一致** | "唯一变量是成像"被破坏，整张对比图作废（最容易犯、最难发现） | 同 `seed` 同 `--instruction-pool`；`check_pairing` 断言 `init_props` 逐位一致；采集后按 `layout_seed` 复核配对率必须 100% |
| **照抄 Uranus 的水体参数** | 本场景相机距离只有 ~0.6m，档位要么没效果要么目标全糊（Euphotic 参数是按 1.2~2.0m 标定的） | M0.5 重标 β / `depth_scale` / `ambient`，并按对比度实测确认档位有梯度 |
| MuJoCo 3.8 雾参数无效 | 以为做了"水下视觉"，其实什么都没变 | 视觉退化只走图像域；MuJoCo 侧只调 `<light>` / `headlight` |
| 一次堆太多任务 | 每任务数据不够，都不收敛 | 中期前**最多 4 个任务**；宁可 3 个各 100 条 |
| `LeRobotDataset.create` 不能续采/覆盖 | 采一半发现格式错，全部重采 | 先采 5 条冒烟 → 全流程跑通（转换+归一化+10 步训练）→ 再大规模采 |
| 相机/光照被改坏 | 现有 320 条数据的分布与新数据不一致 | `base_table.xml` 的 `visual`/`light`/`camera` 块**原样搬运**，不自创 |
| **采集/评测的图像尺寸或预处理不一致** | 训练分布与评测分布不同，数字全废（`WYSD` 就出现过采集 224、评测 256） | 尺寸从单一常量取；自检第 7 项断言两端一致 |
| **释放物体时直跳会弹飞** | 新加的 place 阶段把物体甩出去，成功率虚低（`WYSD` 实测直跳弹飞 17cm） | 张开夹爪必须走**斜坡**（`WYSD` 用 ~3s / 1500 子步）；SO101 的 `_glide` 本身是斜坡，但 place 的"松手"要单独设步数并实测落地误差 |
| **无信息帧占比过高** | 数据集被"原地不动"的帧灌满，训练效率骤降（`WYSD` 实测路点等 settle 时 97% 是原地帧） | 记录器加**帧有效性统计**（动作幅度、物体位移）；采集完打印"有效帧/总帧"；必要时收紧路点等待步数 |
| 力阈值当主判据 | 非单调 + 二值夹爪不可操作（`WYSD` 已否掉一次） | 力只做上限保护，主判据用几何量（见 §4.5） |
| 判据常量在不同文件里各写一份 | 训练判据与评测判据悄悄分叉 | 判据只写在 `specs/criteria.py`，采集与评测都 import 它（`WYSD` 的 `MIN_LIFT` 就是这个模式） |

## 12. 答辩叙事（建议话术）

一页图讲完：

```
┌─────────────────────────────────────────────────────────────┐
│ 链路：MuJoCo 场景系统 ──staging──▶ LeRobot ──▶ π0.5 LoRA ──▶ 闭环评测 │
│                        （本计划负责这一段）                     │
├─────────────────────────────────────────────────────────────┤
│ 场景系统：任务族 P/O/L/D × 每级只加一个难度轴 × 自动判据 + 指令池      │
│   · 准入门槛：场景自检 N 项全绿（IK 可达 / 零干涉 / 静置 / 判据负对照） │
│   · 单一难度轴 ⇒ 级间成功率差值可直接归因（O1 为标尺）                 │
├─────────────────────────────────────────────────────────────┤
│ 三张主图：① 难度阶梯（O1~O5）② 语言消融（换指令动作是否改变）          │
│          ③ 成功率–视觉退化曲线（V0~V3）                          │
└─────────────────────────────────────────────────────────────┘
```

三个卖点：
1. **可扩展**：加一级场景 = 加一个 XML + 一条 `TaskSpec` + 一条判据，不碰训练链路（schema 冻结）。
2. **可归因**：每级只加一个难度轴 + 无障碍基线，差值就是"这一个障碍的代价"。
3. **可信**：实测数字（遮挡率、咬入深度、缝宽余量）+ 场景自检 + 判据负对照，而不是"看起来能抓"。
